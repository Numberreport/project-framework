# <项目名>

把复杂的事情简单化，把简单的事情流程化。

## 模块

模块是负责一项明确工作的单元。每个模块写清五件事：接收什么、怎么做、交付什么、怎样算合格、做不成时怎么办。

模块之间可以接力：前一个模块的交付，就是后一个模块的输入。

**基础模块**：用已有输入完成一次可以直接调用的处理。所需材料可以直接获得。

**组合模块**：把几个模块凑成一项工作。它们合起来做的是一件事，只是这件事没法一次直接做完，要分几步、由几个模块接力，所以把它们合起来看成一个模块。

**怎样划分**：先明确要什么结果、需要哪些材料。材料拿得到就直接用，做成基础模块；这件事没法一次直接做完、要拆成几步接力的，就做成组合模块，让每一步都是一个能直接调用的模块。

**做不成时**：缺材料、缺授权、拿不准，就停下来说明卡在哪、缺什么，交回给人判断，不猜着往下走。已做了一半的，说清哪些完成了、哪些没完成，别把没做成的说成做成了。同一个问题反复失败，说明模块本身可能要改，停下来说清楚再继续。

## 项目

项目由模块组成。

**项目本身也可以是一个模块**：拿它作为别的项目、别的模块的一部分，它对外和基础模块没有区别。

**项目可以处理多项任务**：可以是多个组合合到一起，各自负责一项任务，各有各的入口。

**根目录就是项目**：`modules/` 里放模块，`connections.json` 写模块之间怎么连，两者合起来就是整个项目。

## 模块里写什么

每个模块不管基础还是组合，都写同样的几份文件，对外看和基础模块没有区别。

| 文件 | 写什么 |
| --- | --- |
| `module.json` | 标识、名称、模板版本、状态（`ready` / `pending`）、可选执行入口 |
| `README.md` | 负责什么（“职责”标题下第一段）、怎么用、怎么启动 |
| `INPUT.md` | 接收什么、从哪来、必须满足什么条件 |
| `PROCESS.md` | 怎么做、怎么交接、什么情况停下来问人、做不成时怎么办 |
| `OUTPUT.md` | 交付什么、交给谁、没完成时怎么说明 |
| `VALIDATION.md` | 交付结果怎样才算合格 |
| `SETTINGS.md` | 可选。默认值和当前偏好分开写，偏好不能覆盖必须条件 |

新模块先设 `pending`，写完自检没问题再改 `ready`。

接口要在 `INPUT.md`、`OUTPUT.md` 里用 `interfaces` 代码块写明名称和要求，这是接口的正式依据：

```interfaces
[{ "name": "text", "description": "需要处理的非空文字" }]
```

连接写在 `connections.json`，每条说清三件事：从哪个模块的哪个接口出来、到哪个模块的哪个接口、传的是什么。可选 `when` 写适用条件，`kind` 写 `support`（辅助）或 `return`（退回），都只是给人看的标记，不影响执行。

模块默认直接交付，不要求每步都设检查。要检查时另建一个检查模块，它接收前一模块的交付和原始输入，按前一模块的 `VALIDATION.md` 判定：通过就交给下一个，不通过就写修改意见退回。往返要写清什么情况下停下来。检查模块自己也要合格。

## 东西放哪

| 放什么 | 位置 |
| --- | --- |
| 项目入口、方法、检查工具、画布 | 根目录 |
| 模块 | `modules/` 下每个目录一个，平铺，不套层 |
| 可执行实现 | 模块目录内，如 `run.mjs`；`module.json` 的 `implementation` 填相对模块目录的路径 |
| 参考资料 | 模块内 `knowledge/`，能用原处链接的就别复制 |
| 运行记录、正式成果 | 模块内 `runs/`、`outputs/`，按需建 |

不在根目录散放临时文件。凭据不写进任何文件。

## 做事要求

这些不能不遵守。具体数值（重试几次、留多久）由项目自己定，写进 SETTINGS。

**读文件**：内容变了就重读；文件缺失就停下，不凭记忆代替。

**授权**：读取、修改、发布、付费分别授权，一件事的授权不能顺延到另一件事。改接口、连接、成员、检验标准，增删模块，删除或覆盖已有成果，先说清影响再动。组合不能扩大权限。已授权范围内不重复问。

**失败**：输入不合格不正式处理。超时或结果不明先查原来的任务编号，不要重新提交。其他情况见上面“做不成时”。

**检验**：有业务检验的模块，未通过的产物不能往下游走。检验要说清违反哪条标准、在哪个位置，不能只给一个不通过。

**保存**：明确要求保存的才写进 `outputs/`，同名另存新版本，只有明确说替换才覆盖。`runs/` 按任务标识保存可恢复记录。

**版本**：新项目先 `git init`。动手前核对已有改动，留可恢复版本；一个任务一个提交；提交或推送按已有授权，提交前看差异和验证结果。

**用户偏好**：修改意见和验收反馈只作用于当前任务，不自动记成长期偏好。要记下来时，先说清记什么、放哪个模块的 SETTINGS.md，征求同意；同意记成候选，不等于确认生效，两次分别确认。

**框架问题**：觉得框架哪里不对，先说改法，不擅自改框架本身。要提给框架仓库，用 [框架反馈模块](modules/framework_feedback/README.md)。

## 检查与验收

```bash
node check.mjs          # 结构检查
node check.mjs --verify # 加上模块自带的维护验收
```

脚本只查能机械判断的部分：文件是否齐全、标识是否重复、连接是否指向真实接口、反馈回路有没有停止条件、本地链接是否有效、项目结构是否过期。它查不出接口意思对不对、标准合不合理、内容好不好，那些要人看。

改了模块或连接后，先跑 `node check.mjs --panorama` 更新项目结构，再跑检查。

验收按这三项分开记录：

- **结构**：接口、引用、组合边界、检查脚本通过
- **流程**：输入确实有来源、职责说得通、交接的成败条件合理
- **页面/实际运行**：按同一个具体例子走一遍，看收到什么、产出什么、失败停在哪

改检查脚本本身后，跑 `node --test tests/check.test.mjs`。

## 画布

```bash
node canvas.mjs
```

浏览器打开终端里显示的地址，可以：

- **拖线建连接**：从模块的输出圆点拖到另一个模块的输入圆点。松开后填“传的是什么”，可以再填“什么时候才传”。点击连线改，右键删。拖动标题挪位置。改完点“保存连接”才写盘。
- **打包**：左侧勾选两个以上模块，填标识和名称，先看预览（会移动哪些目录、生成哪些接口、改多少处链接），确认后才执行。打包后新组合是 `pending`，补齐职责和检验标准再改成 `ready`。
- **看配套文件**：点左侧成员，或双击基础模块，可以读它的 README、INPUT、OUTPUT、PROCESS、VALIDATION、SETTINGS。双击组合会进入它内部看连接。

画布只改两样东西：各层的 `connections.json`（真实连接）和根目录的 `canvas-layout.json`（节点位置）。删掉 layout 不影响任何连接。保存前会核对文件有没有被别人改过，改过就拒绝覆盖。服务只监听本机。

## 改造已有项目

先把现有功能、入口、定时任务、数据和未完成任务盘一遍，说清哪些保留、哪些替换、哪些废弃，取得同意再动手。

迁移要分批，每批先说清范围和旧的调用方式怎么兼容。升级模板时对比旧模板、新模板、当前项目三方，保留项目自己的配置和偏好，冲突先问，不直接覆盖。不能只备份代码，历史成果和运行状态也要能恢复。

结构改了要重新生成全景并再跑一次验收。某批验收没过，不要扩大下一批范围。
