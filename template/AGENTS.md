## 项目定义

项目的本质是信息的转化，信息进入项目，通过项目把信息处理为另一种信息。项目由一个个功能模块组成。每个模块可以把输入的信息经过加工处理输出为另一个信息，两个模块可以以信息流的形式连接，上一个模块的输出可以是当前模块的输入，也可以多个模块组成更大的模块协同处理信息。模块中的处理者可以是设定好的程序，也可以是按既定规则工作的 AI。

## 收纳

先查 TREE.md 的「位置」表，按职责找目录：

- 模块 → 「模块」指向的目录，同时在模块表登记。
- 项目特有的实现（不属于任何模块的）→ 「实现」。
- 资料和文档 → 「资料」或「文档」。
- 产出 → 「产出」。
- 任务 → 「状态」目录下的 `tasks.json`，每条有 `id`、`task`、`status`（待办/进行中/完成）、`note`（改了什么）。动手前先写一条「进行中」，提交后改成「完成」，note 写提交摘要。
- 不确定的 → 「暂存」。
- 全局规则 → AGENTS.md，要批。

模板里的 `本体/` 只是示例。迁移已有项目时先改位置表，把职责指到已有目录，不要新建同名目录；一个职责可以对应多个目录；`.gitignore` 按实际的产出和数据位置配置。

有归属就在原处改，没有就提方案，批了再动。难理解的规则补一句依据，不写日期。放进「暂存」的文件和文件夹，名字以 `YYYY-MM-DD-` 开头。TREE 里标成待删的模块，检查会列出来，确认后再删；「暂存」里名称日期超过 30 天的条目，检查也会列出来。根目录允许出现什么，以 `check.mjs` 为准。

## 模块和组合

- 「从哪来」只表示信息从哪个模块传来，不表示上下级；普通模块不写自己属于谁。
- 普通模块按处理者分两类，「谁处理」以「程序：」或「AI：」开头。
- 程序模块同样的输入给出同样的输出，验收脚本能完全判定对错。
- AI 模块每次输出可能不同，验收脚本只查结构（格式、长度、必有项等），内容质量要人审阅，因为脚本判断不了 AI 写得好不好。AI 模块必须写「规则」一节，规则就相当于它的程序，改规则按「边界」里的条款处理。
- 多个模块协作完成复杂任务时，建一个组合模块，同样放「模块」目录、在模块表登记。组合的规格写「成员」「连接」「人工确认」「失败在哪停」，代替普通模块的「谁处理」「失败怎么办」；「输入」「输出」「什么时候跑」「怎么算做对」照写。
- 成员清单是组合归属的唯一来源，成员里不反向写属于哪个组合，因为两处记录迟早会对不上。这条主要靠文档约束，`check.mjs` 只拦常见写法（如「属于哪个组合」「父模块」等节名），写法换了脚本不一定拦得住，AI 不得借换写法绕过。
- 同一模块可以进多个组合，复用同一份实现，不复制；组合可以引用组合，但不能直接或间接包含自己。
- 「连接」每行写 `- 上游 -> 下游：传什么信息`，上下游都必须是本组合的成员。
- 组合验收复用成员的验收结果，只验成员之间的衔接，不重复跑成员里耗时或花钱的任务。

## 边界

- 删信息、改接口或连线、改验收标准、改组合成员、增删模块，先问。
- 接口指「输入」「输出」两节，连线指「从哪来」和组合的「连接」，组合成员指组合的「成员」一节。
- 验收标准包括「怎么算做对」的文字、验收命令，以及它跑到的测试脚本和用例。
- 验收命令一律写成 `node <相对路径>`，路径用 `/`，不要有空格和额外参数；验收脚本必须放在本模块目录内（`check.mjs` 会检查）。
- 把模块从在用改成实验中或待删，先问；实验中转在用可以自主（AI 模块除外），但要跑过验收。
- 改实现、参数（AI 模块除外）、程序模块的规则可以自主，前提是接口和连线不变，且跑过全线检查：`node scripts/check.mjs --verify`。
- 程序模块改规则导致输出变化、验收用例要跟着改的，算改验收标准，先问。
- AI 模块改「规则」、改参数（如提示词变量、模型设置）、把状态从「实验中」改为「在用」，一律先问，因为它的验收只查结构，这些改动都会改变行为，验收通过也说明不了改得对。
- 挪文件、无损合并（一字不差或一段包含另一段）可以直接做，改完也要跑检查。
- 有常驻程序时，结构调整只在维护窗口内做。
- 密钥、凭据、生产配置只读不碰。

## 框架没覆盖的情况

- 停下来提方案，写清会影响哪些文件和规则，批了再改。
- 解决后判断这类情况还会不会再来。会，就把规则写回 AGENTS.md 或对应模块的规格；不会，就只处理这一次。
- 能写成检查的，写进 `check.mjs`，不靠文档提醒。

## 修改意见与用户偏好

用户提出的修改意见、纠错、功能要求和验收反馈，默认用于当前任务，不能直接登记为用户偏好，包括候选偏好。需要留存时，按内容记入任务、设计说明或变更记录。

只有用户明确要求今后沿用，或多次表达出稳定、可复用的个人习惯时，才考虑提炼偏好。登记前先说明拟记录的内容和适用范围，征得用户同意。

用户同意修改当前项目，不等于同意记录长期偏好。修改意见反复出现，也可能说明问题一直没有解决，不能仅凭次数认定为偏好。若项目设有候选与生效状态，同意登记候选不等于确认生效，沿该项目既有确认流程分别处理。

## 框架反馈

框架规则不顺手、互相矛盾、检查误报漏报，或缺了该有的规定，提一份反馈交回模板维护者。框架是从模板复制来的，只在一个项目里改，模板和其他项目都收不到。

- 要提反馈时，先问用户同不同意；同意后再到 https://github.com/Numberreport/project-framework/issues 用「框架反馈」模板提 Issue，一件事一个，保持简短。用户不同意就不提。
- 仓库是公开的，Issue 里不写账号、密钥、个人信息或项目隐私。
- 用不了 GitHub 的，把反馈要点告诉用户，由用户转交。
- 不在项目里直接改框架的通用规则来绕过问题，否则项目和模板会越改越分叉。项目里要临时变通的，按「框架没覆盖的情况」处理，并在 Issue 里注明。
- 「框架没覆盖的情况」解决后要写回的规则，换个项目也适用的，同样提一份反馈。
- 维护者审阅，用户批准后才改模板。关闭 Issue 时写明 `采纳`、`部分采纳` 或 `不采纳`，后两种附原因。

## 版本管理

- 新项目开工先 `git init`。
- 自己动手前先提交一次，保证有干净的回滚点。
- 一个任务一个提交，提交信息写清改了什么。
- 产出、依赖、密钥不进 Git，规则见 `.gitignore`。
