# <项目名>

把复杂的事情简单化，把简单的事情流程化。

## 文档写法

项目维护的 Markdown 文档都按本节编写，包括 README、AGENTS.md、检查标准、提示词和资料说明。各类文件已有的职责和必要结构仍须保留。

- 每份文档用一个一级标题说明主题；需要分节时逐层使用标题，不跳级，不额外编章节号。标题直接说明内容，同级按同一种方式分类，子标题只展开父标题。内容较长的独立主题用标题收纳，不用连续的加粗段首代替分节。
- 按需要设置章节，不强制统一标题，不凑空章节；简单内容可直接写短段或列表。有顺序的操作用编号列表，条件紧跟对应动作。
- 同一概念名称一致，一段只讲一件事。删去没有新增信息的重复表达，避免含糊指代和不必要的术语；必要的条件、例外和依据不能为了缩短而删除。
- 按主题、独立情况或资料用途拆分内容，不设字数硬门槛。正式规定按「内容归位」维护，其他位置引用，不另存一份；代码块、接口和配置示例保留各自格式。
- 模块 README 的五个固定二级标题按「README.md：说明书」保留，需要细分时在其下加子标题；其他类型的 README 不套用这五段。AGENTS.md 按规则主题分类，VALIDATION.md 按验收内容组织，不套用本体的处理步骤。

检查文档和提示词的可读性，可调用[可读性检查模块](modules/prompt_readability/README.md)。

## 模块

模块是负责一项明确工作的单元。每个模块写清六件事：负责什么、接收什么、交付什么、怎么做、没完成时怎么办、怎样算合格。

模块之间可以接力：前一个模块的交付，就是后一个模块的输入。

### 基础模块

用已有输入完成一次可以直接调用的处理。所需材料可以直接获得。

### 组合模块

把几个模块凑成一项工作。它们合起来做的是一件事，只是这件事没法一次直接做完，要分几步、由几个模块接力，所以把它们合起来看成一个模块。

### 怎样划分

先明确要什么结果、需要哪些材料。材料拿得到就直接用，做成基础模块；这件事没法一次直接做完、要拆成几步接力的，就做成组合模块，让每一步都是一个能直接调用的模块。

### 接口

模块对外接什么、交什么，用 `interfaces` 代码块写：接收的写在 README 的「输入」里，交出的写在「输出」里，各一块。

### 连接

模块之间怎么连写在 `connections.json`，每条说清三件事：从哪个模块的哪个接口出来、到哪个模块的哪个接口、传的是什么。可选 `when` 写适用条件，由实际执行方式判断；使用 `run.mjs` 时必须接入条件判断。`kind` 写 `support`（辅助）或 `return`（退回），只是给人看的标记，不影响执行。

### 画布

连接和结构还能用画布看和改，用法见 [画布说明](canvas/README.md)。AI 新建或调整节点、连接后，须按其中的布局要求整理并检查整体效果。

### 流程引导

需要逐步协作时使用[流程引导模块](modules/workflow_guidance/README.md)。引导设置归所属项目或组合的登记表，只引用正式成员；接力仍按连接进行。确认方式可选择不额外确认、仅关键步骤确认或逐步确认。设置与接入见[流程引导接入](README.md#流程引导接入)。

确认放在成员完成、成果交给后续步骤之前。需要质量检查的工作仍按「VALIDATION.md：检查标准」组成生成与检查组合，在组合交付处设置确认。用户确认不代替质量检查；关闭可选确认不免除缺材料、必要业务决定或其他权限规定要求的停顿。

### 正式结构绑定

正式画布从项目文件生成，不另存一套结构。调整模块、组合归属、接口或连接时，先修改正式登记、接口、连接及受影响的实现，再由画布反映并验收。草稿只供试改，采纳后也按此顺序落地；纯布局和样式可只改画布。实际运行可采用 `run.mjs`，也可保留原入口，但都须验证实际调用与正式结构一致，不能只靠约定。接入方式见 [执行说明](README.md#正式执行)。

### 检查

改完模块或连接，跑 `node check.mjs` 查有没有搭错。它遍历整个项目的正式模块，检查模板版本、配套文件、固定章节是否缺失、重复或为空、接口位置、标识、连接、反馈停止条件和本地链接，并查找正式层级外的模块登记。运行数据、依赖、缓存及构建目录不参与模块查找。模块分工是否合理、内容是否归位、实际调用是否与正式结构一致，仍须结合内容和执行证据检查，不能凭结构检查通过认定整个项目符合框架。加 `--verify` 再跑各模块自带的验收。

维护验收中，上游待配置或验收失败时，跳过依赖它的下游模块。连线经过组合输入时，按对应接口追到内部成员。使用其他独立输入的成员可以继续验收。

需要检查项目目标、模块分工、完整流程和实际结果时，可调用[项目整体检查模块](modules/project_overall/README.md)。它与项目口径、可读性两个检查配套，调用方式及三项配套检查的安排见该模块说明；结构检查仍按上面的命令执行。

## 项目

项目由模块组成。

### 项目本身也可以是一个模块

拿它作为别的项目、别的模块的一部分，它对外和基础模块没有区别。项目要接的输入、要交的结果，写在根目录 README 的「输入」「输出」里，接给哪个模块写在 `connections.json` 里。

### 项目可以处理多项任务

可以是多个组合合到一起，各自负责一项任务，各有各的入口。

### 根目录就是项目

`modules/` 里放模块，`connections.json` 写模块之间怎么连，两者合起来就是整个项目。

### 前端、代码与画布

有前端页面的项目，可以从三个层面理解：

- **前端页面**：供用户使用项目，页面怎么设计不由本框架规定。
- **底层代码与项目文件**：实现功能，定义模块、接口和连接，是前端页面和画布的共同依据。
- **中端画布**：供人查看和调整模块结构，具体用法见 [画布说明](canvas/README.md)。

前端页面一般由 AI 修改。修改底层功能时，AI 应同时更新受影响的前端页面；从前端页面发起功能调整时，也应修改对应的底层代码与项目文件。涉及模块、接口或连接的变化，再通过这些文件反映到画布。只调整页面外观时，不要求修改底层逻辑。

## 模块里写什么

### 文件一览

每个模块不管基础还是组合，都写这几样，对外看和基础模块没有区别。

- `README.md`：说明书
- `module.json`：登记表
- 本体
- `VALIDATION.md`：检查标准

### README.md：说明书

模块的说明书，也是对外说明。写五段，标题名字固定，检查脚本按名字找：

| 标题 | 写什么 |
| --- | --- |
| `## 职责` | 一句话说清负责什么 |
| `## 输入` | 接收什么 |
| `## 输出` | 交付什么 |
| `## 处理流程` | 正常情况下怎么做、怎么用本体 |
| `## 没完成时` | 什么情况停下来问人；停下后说清卡在哪、缺什么；做了一半的说清哪些完成了、哪些没完成；反复失败说明模块可能要改 |

### module.json：登记表

模块的登记表，程序靠它认模块。基本项如下：

- 标识（`id`）：英文短名，只能用字母、数字、下划线和短横线，如 `framework_feedback`。同一项目里不能重名。
- 名称（`name`）：给人看的中文名。
- 模板版本（`template`）：按框架哪一版写的。以后升级框架时，靠它判断哪些模块要迁移。
- 状态（`status`）：`ready` 是写好了能用；`pending` 是还没写完，仍须通过结构检查，但跳过模块验收，不得运行。
- 执行入口（`implementation`）：基础模块为 ready 时必填，路径相对模块目录。程序模块填程序入口，AI 模块填主提示词；正文就是本体时填 `README.md`。组合沿用项目自己的入口时可登记，但实际调用须与内部连接一致；采用 `run.mjs` 调度时组合不另设入口。

```json
{
  "id": "framework_feedback",
  "name": "框架反馈",
  "template": {
    "id": "project-framework",
    "version": "3.0.0"
  },
  "status": "ready",
  "implementation": "implementation/instructions.md"
}
```

根项目自己的页面、资料等放在根目录时，在根 `module.json` 的可选 `rootFiles` 数组中登记，例如 `"rootFiles": ["index.html", "assets"]`。每项填写已存在的根目录文件或目录名称，不写路径、通配符或密钥；模块内容仍放对应模块。框架自带文件和常用构建配置无需另行登记。

### 本体

真正干活的东西，用 `implementation` 指向入口。两种做法：

- 程序模块：本体是一堆代码文件，入口填能直接运行的那个，如 `run.mjs`。
- AI 模块：本体是提示词，入口填主提示词，如 `prompt.md`。

#### AI 本体提示词的写法

通用格式遵循「文档写法」，本体另外遵守：

- 引用本模块的说明书和检查标准，不重复抄写；本体只写具体处理方式。
- 各情况专用的资料放在该情况的资料目录，多个情况共用的资料集中存放一份；各处理方式写清何时读取哪些资料。目录结构见下方 AI 本体示例。
- 主提示词写清各情况的适用条件，以及多个条件同时符合、都不符合或无法判断时怎么办。

参考 [AI 本体示例](modules/ai_example/README.md)，把其中的 `implementation/` 复制到模块里，按实际工作填写。

#### 个性化定制

- 参数、开关、方法选择等配置用 JSON，与本体分开；程序或提示词写清如何读取和使用。供程序读取的输入输出按接口要求，不受本体正文格式限制。
- 程序模块：用户修改配置中的可调值，不动代码。
- AI 模块：可以备几套提示词，在配置中选择当前生效的一套，不改提示词正文。

### VALIDATION.md：检查标准

检查标准用来判定本模块的输出算不算合格。

模块默认直接输出成果。需要验收业务产物时，谁交付产物，谁负责安排检查：把生成模块和检查模块放进同一个组合，生成后紧接检查，通过后才由组合对外交付。检查模块接收生成模块的输入、产物和检查标准；不通过时，写明问题并退回修改，重新检查通过后再交付。

检查模块同样按通用模块模板写，只是职责换成了检查。因此它自己也有检查标准，它的输出也可以再交给别的检查模块检查。

## 做事要求

### 模块状态

新模块先设 `pending`，写完自检没问题再改 `ready`。

### 同步修改

改功能时，同时修改受影响的本体、接口和连接，并通过结构检查与实际接力验证。运行期间正式文件有变化，停止接力，核对后重新运行；不能把旧结果继续交给下游。画布显示一致不代表业务内容已验收。

### 删除与验收

删除模块须清除对应正式目录、相关连线及失效调用，检查代码、提示词和任务入口中的引用；共享实现仍被其他模块使用时保留。用同一份具体输入核对修改前后的实际处理和画布，再在没有布局文件的副本中重建画布，确认节点、接口、组合归属和连线仍与正式结构一致。只隐藏卡片或只通过结构检查，不算完成。

### 内容归位

每项规则只有一个正式出处，按当前模板归入说明书、本体或检查标准；其他位置引用，不重复保存，不擅自创建新分类。

### 只留现行做法

尝试过程和未采用方案不写入长期工作文件。采用新方案时，清除被替代的规则、示例和引用，不另留历史副本。

### 修改后检查

修改后调用[项目口径检查模块](modules/project_consistency/README.md)检查受影响内容；准备交付或用户要求全面检查时，检查整个项目，不另设定时任务。当前智能体负责修复并再次调用该模块复查；涉及业务取舍且没有明确依据时，先请用户决定。未解决问题和检查限制须明确交代；结构检查不能代替内容检查。

### 修改意见

记录修改意见时，提炼原意，只写具体做法。

### 框架问题

觉得框架哪里不对，先说改法，不擅自改框架本身。要提给框架仓库，用 [框架反馈模块](modules/framework_feedback/README.md)。

## 运行与存档

### 任务

项目搭好后会被反复调用，每次调用是一项任务。同时可以有多个任务，各自分开。

### 一次运行

任务的一次执行叫运行。运行会产出交付物，也会改变这个任务的状态，比如做到哪、交了什么。

### 存档

每个任务各有自己的存档，放在一起的还有产物。每次运行结束时把最新状态存下来，覆盖上一次，只留最新一份。要回看以前，由项目自己另加。

### 产物

产物和存档放在一起。留不留看需要：没完成的中间结果随存档走，要长期用的是否另留由模块自己定。

### 接着走

下次运行时先读这个任务的存档，知道上次做到哪。出错或中断就从存档接着走，不从零开始。存档缺失或不完整，停下来说明，不猜。

### 放哪

存档和产物都放项目根目录的 `workspace/`，每个任务一个子目录，名字能分清就行。里面放这个任务的最新状态和产物，状态文件叫什么、写什么由模块自己定，够下次接着跑就行：做到哪个模块、每步交了什么、缺什么。

```text
项目/
  workspace/
    <任务>/      最新状态 + 这个任务的产物
```

`workspace/` 是数据不是代码，不进版本管理。业务产物和业务状态由模块本体保存；采用流程引导的执行入口另存调度状态，恢复用法见[流程引导接入](README.md#流程引导接入)。
