# <项目名>

> 开工先读 [项目方法](METHOD.md)，再看本次相关的模块。内容变了就重读；文件缺失就停下，不凭记忆代替。
> 开工跑 `node check.mjs`，收尾跑 `node check.mjs --verify`。需要 Node 18+。检查通过不代表内容合格。

## 东西放哪

| 放什么 | 位置 |
| --- | --- |
| 项目入口、方法、检查工具、画布 | 根目录 |
| 模块 | `modules/` 下每个目录一个，平铺，不套层 |
| 可执行实现 | 模块目录内，如 `run.mjs`；`module.json` 的 `implementation` 指过去 |
| 参考资料 | 模块内 `knowledge/`，按需建 |
| 运行记录、正式成果 | 模块内 `runs/`、`outputs/`，按需建 |

不在根目录散放临时文件。凭据不写进任何文件。

## 边界

改接口、连接、成员、检验标准，增删模块，删除或覆盖已有成果：先说清影响，取得授权再动。已授权范围内不重复问。

读取、修改、发布、付费分别授权，组合不扩大权限。密钥不进模板、知识、记录或 Git。

## 用户偏好

修改意见和验收反馈只作用于当前任务，不自动记成长期偏好。要记下来时，先说清记什么、放哪个模块的 SETTINGS.md，征求同意；同意记成候选，不等于确认生效，两次分别确认。

## 版本

动手前核对已有改动，留可恢复版本。一个任务一个提交，提交前看差异和验证结果。提交或推送按已有授权。

## 框架问题

用框架时觉得哪里不对，先说改法，不擅自改框架本身。要提给框架仓库，用 [框架反馈模块](modules/framework_feedback/README.md)。
