# 项目方法

**把复杂的事情简单化，把简单的事情流程化。**

## 从信息的处理和传递出发

先明确需要什么结果，再确定需要哪些输入、经过哪些处理，以及信息如何传递。涉及发送、发布等实际操作时，也要说明操作及其结果。

- **普通模块**完成一项明确的处理，有自己的输入、处理和输出。默认不细拆，有明确好处才拆。
- **组合模块**组织多个普通模块或组合模块。输入交给内部入口模块，经过处理和传递，形成对外输出。
- **项目**围绕总体目标组织模块，可以提供多个任务入口，启动不同流程。无论组合多少层，最终都由普通模块构成。

## 用同一套模板讲清楚

| 内容 | 要说明什么 |
| --- | --- |
| 输入 | 需要什么信息，有什么要求，来自哪里 |
| 处理流程 | 怎样处理和传递信息，需要参考什么资料 |
| 输出 | 交付什么，未完成时怎样说明 |
| 检验标准 | 什么样的结果才算合格 |
| 使用说明 | 用来做什么，怎样用，有什么限制 |

普通模块和组合模块都适用。模板统一，具体要求各自维护，不强求共享实现。方法本身不要求五项各建一个文件，也不为填模板而重复内容。

目标是**说得清、改得动、看得懂，出问题能定位到模块**。就像公司运转出问题时，要能找到问题出在哪个人或哪几个人；项目也要能定位到一个模块或一串模块。

同一件事一处维护正式依据，分清讨论与定稿、新旧方案、要求与实际；模块职责和依赖清楚，内部变化尽量不影响外部；用最少的必要文字，让没有背景的人也能理解。发现冲突时，有明确的已确认依据就统一，无法判断才询问。

## 三层可视化

「看得见」分三层，勿混用：

1. **项目底层结构**：模块、连接、文件——项目本身。正式依据在各模块配套文件与 connections.json。
2. **底层结构可视化**：画布、全景——方便开发者看清和改连接，不面向最终用户。见 [可编辑项目画布](canvas.md)、[TREE.md · 项目全景](../TREE.md#项目全景)。
3. **前端可视化**：面向用户的界面——按任务另建，不跟第二层混成一套工具。本方法只定此边界，不规定具体前端技术。

分层是为避免开发者用的结构可视化与面向用户的界面共用同一套工具或说明。

## 按需要使用配套说明

以下指引说明当前模板的具体做法。文件和连接格式以 [模块模板](module-template.md) 为准，执行相关任务时遵守运行约定。

每次任务读本页，再按需阅读。内容变化后重读；缺失时停止依赖它的操作。

| 任务 | 阅读 |
| --- | --- |
| 设计模块、组合与输入输出 | [设计](design.md) |
| 新建或配置一套模块文件 | [模块模板与中文对照](module-template.md) |
| 修改或迁移 | [实施](implementation.md) |
| 运行、授权、检验修正、保存、清理、恢复 | [运行与维护](operation.md) |
| 检查与交付 | [验收](acceptance.md) |
| 配置检查 | [配置检验标准](CONFIG_VALIDATION.md) |
| 查看和修改连接（第二层） | [可编辑项目画布](canvas.md) |

共同要求只在对应指引维护，模块文件说明当前位置的实际要求，不复制整套方法。权限见 [AGENTS.md](../AGENTS.md)，位置见 [TREE.md](../TREE.md)。检查不证明阅读、理解或业务质量。

当前模板提供文件结构、执行约定、配置检查、全景与可运行示例。分身调度、自动检验修正、定时运行、清理和升级由项目按流程实现或智能体执行，不包含自动运行这些流程的后台服务。
