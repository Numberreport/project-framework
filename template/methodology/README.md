# 项目方法

**把复杂的事情简单化，把简单的事情流程化。**

## 模块的划分与组合

模块是负责一项明确工作的单元。每个模块明确接收什么、工作流程、交付什么，交付成果的检验标准，以及说明失败后怎么办。

- 普通模块：用已有输入，完成一次可直接调用的处理，输出相应内容，不展开这项能力的内部实现。输入可以直接提供，也可以来自其他模块的输出。
- 组合模块：组织多个普通模块或组合模块，共同完成一项独立职责。
- 项目：围绕总体目标组织模块，可以有多个任务入口。

### 怎样划分

项目开始时，先明确要什么结果、需要哪些材料。材料能直接取得就使用，需要加工就先安排相应处理，理清各项处理之间的依赖，再划分模块。

需要加工才能得到的输入，另设前置模块，再按同样方法判断，直到可直接调用的能力为止。小步骤和辅助处理也用这个标准。

职责写清负责什么。

### 怎样组合

组合模块在功能上与普通模块一致，写清接收什么、工作流程、交付什么。工作流程由多个模块协同完成。

### 输入与交接

每项输入写清来自用户上传、其他模块输出还是已保存材料。

## 五份文件，各管一件事

| 文件 | 要说明什么 |
| --- | --- |
| README.md | 负责什么、怎样使用及外部工具 |
| INPUT.md | 接收什么、来自哪里、须满足什么条件 |
| PROCESS.md | 怎样处理和交接，何时停止、失败或请求确认 |
| OUTPUT.md | 交付什么、交给谁、未完成时怎样说明 |
| VALIDATION.md | 交付结果怎样才算合格 |

普通模块、组合模块和项目根目录沿用这套文件，各位置维护自己的实际要求。职责只在 README.md 维护，其他内容引用对应文件，不重复存储。字段和路径格式见[模块模板](module-template.md)。

同一件事一处维护正式依据，分清讨论与定稿、新旧方案、要求与实际。用最少的必要文字讲清职责和依赖；发现冲突时，有明确的已确认依据就统一，无法判断才询问。

## 三层可视化

1. **用户前端**：最终用户使用的界面，由具体项目决定。
2. **构建者中端**：构建者查看模块职责、输入输出、组合和连接，定位问题，并在授权范围内调整结构的工作界面。画布和全景属于这一层。
3. **底层代码与执行实现**：实际完成处理的程序、AI 执行指引及其调用方式；中端须能找到对应实现。

本方法只规定中端和底层，不规定用户前端的样式或技术，也不把中端当作用户前端。模块文件和 connections.json 是正式依据；中端读取它们，不另存一套职责或关系。展示结构不等于执行流程，具体能力及待实现项见[画布说明](canvas.md)。

## 按需要使用配套说明

以下指引说明当前模板的具体做法。文件和连接格式以 [模块模板](module-template.md) 为准，执行相关任务时遵守运行约定。

每次任务读本页，再按需阅读。内容变化后重读；缺失时停止依赖它的操作。

| 任务 | 阅读 |
| --- | --- |
| 设计模块、组合与输入输出 | 本页[模块的划分与组合](#模块的划分与组合) |
| 新建或配置一套模块文件 | [模块模板与中文对照](module-template.md) |
| 修改或迁移 | [实施](implementation.md) |
| 运行、授权、检验修正、保存、清理、恢复 | [运行与维护](operation.md) |
| 检查与交付 | [验收](acceptance.md) |
| 配置检查 | [配置检验标准](CONFIG_VALIDATION.md) |
| 查看和修改连接（第二层） | [可编辑项目画布](canvas.md) |

共同要求只在对应指引维护，模块文件说明当前位置的实际要求，不复制整套方法。权限见 [AGENTS.md](../AGENTS.md)，位置见 [TREE.md](../TREE.md)。检查不证明阅读、理解或业务质量。

当前模板提供文件结构、执行约定、配置检查、全景与可运行示例。分身调度、自动检验修正、定时运行、清理和升级由项目按流程实现或智能体执行，不包含自动运行这些流程的后台服务。
