# 项目方法

**把复杂的事情简单化，把简单的事情流程化。**

## 一、模块

模块是负责一项明确工作的单元。每个模块写清四件事：接收什么、怎么做、交付什么、怎样算合格。

- **普通模块**：用已有输入完成一次可以直接调用的处理。
- **组合模块**：把多个模块凑成一项完整任务，前一个的交付就是后一个的输入。
- **项目**：根目录本身按组合处理，可以有多个任务入口。

### 怎样划分

先明确要什么结果、需要哪些材料。材料拿得到就直接用；要加工才能拿到的，先给它安排一个模块，再往下看它自己的材料从哪来，直到每一步都能直接调用为止。小步骤和辅助处理也用这个标准。

拿不准要不要拆的时候，先不拆。一个模块里写清楚，比拆成两个还要互相交代便宜。

### 怎样组合

只有多个模块确实要凑成一项完整任务时才建组合。组合对外和普通模块一样：有自己的输入输出、自己的五份文件。成员放在组合的 `modules/` 里，连接写在 `connections.json`。

不要为了整齐而套层。模板默认平铺，示例就是两个并列模块。

### 检查与退回

模块默认直接交付，不要求每步都设检查。要检查时另建一个检查模块，它接收前一模块的交付和原始输入，按前一模块的 `VALIDATION.md` 判定：通过就交给下一个，不通过就写修改意见退回。往返时写清什么情况下停下来。

检查模块也是模块，自己也要合格；需要时同样可以给它接检查。不通过不等于返工无限循环，写清停止条件是硬性要求。

## 二、每个模块写什么

| 文件 | 写什么 |
| --- | --- |
| `module.json` | 标识、名称、模板版本、状态（`ready` / `pending`）、可选执行入口 |
| `README.md` | 负责什么（“职责”标题下第一段）、怎么用、怎么启动 |
| `INPUT.md` | 接收什么、从哪来、必须满足什么条件 |
| `PROCESS.md` | 怎么做、怎么交接、什么情况停下来问人 |
| `OUTPUT.md` | 交付什么、交给谁、没完成时怎么说明 |
| `VALIDATION.md` | 交付结果怎样才算合格 |
| `SETTINGS.md` | 可选。默认值和当前偏好分开写，偏好不能覆盖必须条件 |

职责只在 README 里写一次，别处引用它，不要抄一遍。

需要时再建这几个目录，不是每个模块都得有：

- `implementation/` — 程序或 AI 执行指引，由 `module.json` 的 `implementation` 指过去
- `knowledge/` — 参考资料，能用原处链接的就别复制
- `runs/` — 运行记录
- `outputs/` — 正式成果

接口要在 `INPUT.md`、`OUTPUT.md` 里用 `interfaces` 代码块写明名称和要求，这是接口的正式依据：

```interfaces
[{ "name": "text", "description": "需要处理的非空文字" }]
```

连接写在 `connections.json`，每条说清三件事：从哪个模块的哪个接口出来、到哪个模块的哪个接口、传的是什么。可选 `when` 写适用条件，`kind` 写 `support`（辅助）或 `return`（退回），都只是给人看的标记，不影响执行。

## 三、执行时的硬性要求

这些不能不遵守。具体数值（重试几次、留多久）由项目自己定，写进 SETTINGS。

**授权**：读取、修改、发布、付费分别授权，一件事的授权不能顺延到另一件事。组合不能扩大权限。账号密钥不进模板、知识库、记录和 Git。

**失败**：输入不合格不正式处理。缺材料、缺授权、拿不准的时候停下来问，别猜。超时或结果不明先查原来的任务编号，不要重新提交。

**检验**：有业务检验的模块，未通过的产物不能往下游走。检验要说清违反哪条标准、在哪个位置，不能只给一个不通过。

**保存**：明确要求保存的才写进 `outputs/`，同名另存新版本，只有明确说替换才覆盖。`runs/` 按任务标识保存可恢复记录。

**修改**：改接口、连接、成员、检验标准，删或覆盖已有成果，先说清影响并取得授权。已授权的范围内不重复问。

**版本**：新项目先 `git init`。动手前核对已有改动，留可恢复版本；一个任务一个提交；上线前说明差异和验证结果。

## 四、画布

```bash
node canvas.mjs
```

浏览器打开终端里显示的地址，可以：

- **拖线建连接**：从模块的输出圆点拖到另一个模块的输入圆点。松开后填“传的是什么”，可以再填“什么时候才传”。点击连线改，右键删。拖动标题挪位置。改完点“保存连接”才写盘。
- **打包**：左侧勾选两个以上模块，填标识和名称，先看预览（会移动哪些目录、生成哪些接口、改多少处链接），确认后才执行。打包后新组合是 `pending`，补齐职责和检验标准再改成 `ready`。
- **看配套文件**：点左侧成员，或双击普通模块，可以读它的 README、INPUT、OUTPUT、PROCESS、VALIDATION、SETTINGS。双击组合会进入它内部看连接。

画布只改两样东西：各层的 `connections.json`（真实连接）和根目录的 `canvas-layout.json`（节点位置）。删掉 layout 不影响任何连接。保存前会核对文件有没有被别人改过，改过就拒绝覆盖。服务只监听本机。

## 五、验收

```bash
node check.mjs          # 结构检查
node check.mjs --verify # 加上模块自带的维护验收
```

脚本只查能机械判断的部分：文件是否齐全、标识是否重复、连接是否指向真实接口、反馈回路有没有停止条件、本地链接是否有效、全景是否过期。它查不出接口意思对不对、标准合不合理、内容好不好，那些要人看。

结构验收按这三项分开记录：

- **结构**：接口、引用、组合边界、检查脚本通过
- **流程**：输入确实有来源、职责说得通、交接的成败条件合理
- **页面/实际运行**：按同一个具体例子走一遍，看收到什么、产出什么、失败停在哪

改检查脚本本身后，跑 `node --test tests/check.test.mjs`。

## 六、改造已有项目

先把现有功能、入口、定时任务、数据和未完成任务盘一遍，说清哪些保留、哪些替换、哪些废弃，取得同意再动手。

迁移要分批，每批先说清范围和旧的调用方式怎么兼容。升级模板时对比旧模板、新模板、当前项目三方，保留项目自己的配置和偏好，冲突先问，不直接覆盖。不能只备份代码，历史成果和运行状态也要能恢复。

结构改了要重新生成全景并再跑一次验收。某批验收没过，不要扩大下一批范围。
